# Sets for quick games (« parties »)

Status: grilling. Decisions are written here as they land.

## Idea

A quick game (`tournaments.kind = 'game'`) can be played as a match of N sets,
tennis-style: e.g. best of 3 sets of 11 points. Tournaments are out of scope.
In a ranked game, Elo must take the sets into account.

## How Elo works today (src/lib/rating.ts)

Each finished match is one Glicko-2 update: winner `s = 1`, loser `s = 0`,
weighted by `w = w_margin × w_stakes`, where
`w_margin = 1 + 0.75 × (point gap / target)`, capped at 1.75. Quick games have
`w_stakes = 1`.

Simulated deltas for two evenly matched regulars (1500, RD 110), scratch script
copying the engine's math (not the engine itself):

| Result                               | Each set is a game | One result per match |
|--------------------------------------|-------------------:|---------------------:|
| Single game 11-5 (today)             | +41.5              | +50.1                |
| Bo3 2-0 (11-5, 11-7)                 | +68.4              | +50.1                |
| Bo3 2-1 (11-5, 8-11, 11-9)           | +30.0              | +40.6                |
| Bo3 1-2 (11-2, 9-11, 10-12)          | −21.9              | −40.6                |
| Bo5 3-0 (11-5 ×3)                    | +93.2              | +50.1                |
| Bo5 3-2 (all 11-9 / 9-11)            | +21.8              | +37.3                |

## Decisions

1. **Elo: one result per match.** A ranked match of sets is one Glicko-2
   update: the match winner gets `s = 1`, the loser `s = 0`, so the winner
   always gains. The weight comes from the set score, using today's margin
   formula with sets as the unit:
   `w_margin = 1 + 0.75 × (set gap / sets needed to win)`, capped at 1.75
   (Bo3: 2-0 → 1.75, 2-1 → 1.375; Bo5: 3-0 → 1.75, 3-1 → 1.5, 3-2 → 1.25).
   Points inside the sets don't affect the weight. Match length adds no extra
   weight: a Bo5 counts as much as a single game. Single-game parties keep
   today's point-margin weight unchanged.

2. **Best of N.** "3 sets" means first to 2: the match ends once a player has
   won a majority of N. N is odd.

3. **Form offers 1 · 3 · 5 sets as chips**, defaulting to 1, so a party
   plays as today unless someone picks more. The points chips are unchanged
   and set the points per set.

4. **A won set waits for « Valider le set ».** « −1 point » still corrects
   until the tap. Validating starts the next set at 0-0, and validating the
   deciding set ends the match (today's `done` + `ended_at`). A validated set
   is locked.
5. **Serve follows the ITTF rule (default, not asked):** whoever served first
   in a set receives first in the next one. Within a set, today's
   every-2-points / deuce rule applies, counted on that set's points.

6. **A capot is any set won to 0.** CapotScreen shows when that set is
   validated, and stats, records and Slack count one capot per set.

7. **Point totals add up every set; point records compare single sets.**
   Points for/against, difference and total points sum all sets played.
   « Plus large victoire » and « match le plus serré » rank individual sets
   alongside single games.

8. **Only true match balls count**, meaning the next point would win the
   whole match. A point that would only win an earlier set shows a « balle de
   set » pill on the scorer and is not tracked. `mb_saved_a/b` keep their
   meaning.

9. **Pronostics are out of scope.** The user says betting doesn't work today
   and they don't care about it, so nothing is adapted for sets. Whatever bets
   show up on a set match settle however they happen to.

10. **Chaos Mode is out of scope**, like pronostics: no set-aware behaviour.
    The only guard is the storage design: legendaries touch the live
    `score_a/b` only, so they can't rewrite a validated set.
11. **Doubles can use sets (default, not asked).** Doubles are always
    unranked, so no Elo is involved. The scorer is the same.
12. **A rematch keeps the set count (default, not asked)**, as it already
    keeps target, unranked and teams.

13. **Display uses set scores only, tennis-scoreboard style**, with no
    separate set tally:

    ```
    Finished                 Live
      Léo   11   8  11        Léo   11   8   7 •
      Inès   5  11   9        Inès   5  11   5
    ```

    Defaults, not asked: compact one-line places (Parties history row,
    RecentResults, rating-chart tooltip, player-card last 8) read
    `11-5 8-11 11-9` from the winner's side. Slack says « l'emporte (11-5,
    8-11, 11-9) ». Single games display exactly as today.
14. **Duration estimate (default, not asked):** expected number of sets ×
    the per-set estimate. Calibration reads the points of each set.

## Proposed storage (engineering default, to confirm)

- `tournaments.best_of int not null default 1`. Every existing row reads as
  a single game.
- `matches.sets jsonb not null default '[]'`: the **validated, non-final**
  sets as `[[a, b], …]`.
- `score_a/score_b` keep meaning **the points of the set in play**, and
  after `done`, of the deciding set. In best-of-N the deciding set is always
  won by the match winner, so every consumer that only needs the winner
  stays correct without changes. That includes the rating replay's winner and
  draw-skip, `computeStandings`'s champion, head-to-head, rivalries and the
  Slack streaks. Single games
  are untouched: `sets` stays `[]`.
- Point consumers (totals, records, capots, the Elo weight, displays,
  duration) read "all sets" = `sets` + the final `[score_a, score_b]` through
  one helper.
- Realtime echo reconciliation (`realtimeSync.ts`) must include `sets`.
- Chaos legendaries only touch `score_a/b`, so they can't reach a validated
  set (decision 10).

## Split

match of sets. The scorer runs it set by set, and the result counts in Elo
(when ranked), stats, history and Slack. Today a party is a single game: a
longer match means playing several separate parties, and each one moves Elo
as if it were a whole match.

**Recommended first slice: S1.** Players can play a « non classée » Bo3/Bo5
party from creation to result.

Why this first: it proves the whole path (form → schema → scorer → realtime
→ result) and writes the new data shape for real, while Elo can't be wrong
because set parties are forced unranked, the same way doubles already are.

## S1 acceptance criteria added by find-gaps (2026-10-22)

- **AC-S1-1 (undoing a set validation).** Given a Bo3/Bo5 where a set has just
  been validated and the new set is still 0-0, when the ref taps « Annuler »,
  then the previous set comes back as the set in play with its score
  unvalidated (e.g. 11-9), so « −1 point » can correct it. The undo is read from
  the stored `sets`, not the in-memory undo stack, so it also works after a
  reload or from another device. Once a point is scored in the new set, the
  previous set is locked and « Annuler » only undoes points of the current set.
  As built (step 6): « Annuler » first undoes the current set's points; when
  the new set is back to 0-0 with nothing left to undo, it can take back the
  validation again. "Locked" means locked while the new set has points;
  enforcing more would need extra stored state.
  Validating the deciding set ends the match and can't be undone, as today.
- **AC-S1-2 (no Slack for set parties yet).** Given a party created with 3 or
  5 sets, then no Slack invitation is sent at creation and no result is posted
  when it ends. Single-set parties post exactly as today. S4 turns Slack on for
  set parties, with the set lines. Set parties played before S4 stay
  unannounced, and S4 does not post them retroactively.
- **AC-S1-3 (scorer strip).** Given a Bo3/Bo5 in play, the scorer's tap zones
  are unchanged (big current-set score, « −1 point »), and the line that says
  « Jeu en 11 » today (top bar on desktop, meta bar on a phone) reads
  « Bo3 en 11 · Set 3 · 11-5  8-11 ». The finished sets are listed in the order
  the zones are displayed, so they follow the left/right swap. In set 1 it reads
  « Bo3 en 11 · Set 1 ». Single-set parties still read « Jeu en 11 ».
- **AC-S1-4 (serve per set).** Given A served first in set 1 of a Bo3, when
  set 1 is validated, then B serves first in set 2 and A in set 3. Given any
  set at 0-0 (set 2 included), the serve swap button swaps that set's first
  server, and later sets alternate from the corrected one. Once a point is
  scored in a set, the button is disabled for that set, as today. Within a set,
  serve changes every 2 points and every point at deuce, on that set's points.
- **AC-S1-5 (no capot moments for set parties until S5).** Given a set party,
  when a set or the match ends with a score to 0, then no CapotScreen shows,
  and the scorer pill at 10-0 reads « balle de set » or « balle de match », not
  capot. S5 brings capots to set parties: CapotScreen at « Valider le set »,
  the pill, stats and Slack. Single-set parties keep today's capot behaviour.
- **AC-S1-6 (technical, not asked).**
  - The migration adds `tournaments.best_of int not null default 1` and
    `matches.sets jsonb not null default '[]'`. It is applied to production
    before the deploy and proven on local Postgres first.
  - Readers treat a missing `best_of` as 1 and missing `sets` as `[]`, like
    `unranked`.
  - « Valider le set » writes the whole `sets` array (never an append), so two
    devices validating the same set write the same value.
  - Realtime echo reconciliation includes `sets`.
  - Chaos legendaries only touch `score_a/b`.

## Parking lot

- Pronostics and Chaos Mode on set matches (decisions 9, 10).
- Tournaments with sets (out of scope from the start).
- Per-set clock on the scorer (find-gaps, Nice-to-have): the chrono stays
  match-wide in S1.

## Warnings

- Between S1 and S5, stats from set parties count only the deciding set.
  They are derived, so S5 corrects them retroactively; `mb_saved` is stored,
  which is why S1 already writes it correctly.
- Set parties played between S1 and S2 stay « non classée » forever (the flag
  is on the row). If that matters, ship S1 and S2 together.

# Plan: S1, play an unranked Bo3/Bo5 party

**Branch**: feat/game-sets
**Status**: Active, awaiting approval

## Goal

Players can create a « non classée » Bo3 or Bo5 party and score it set by set
on the board and /ref, through to the result.

## Acceptance criteria

The S1 row of the split table (its examples), plus AC-S1-1 … AC-S1-6 above.

Test levels: the set rules are pure functions with unit tests (`*.test.ts`,
node). Scorer interaction goes through browser tests on the props-driven
`LiveScorer` (`*.browser.test.tsx`, with an `onPatch` spy, no `vi.mock`, see
memory). Form layout and copy are checked by eye in the running app, not by
tests.

## Release order

Steps 1–6 ship dark. No set party can exist until step 7 adds the chips,
because `best_of` is always 1 until then. Every step stays deployable, and
single-set parties behave exactly as today at each one.

## Steps

Every step follows RED-GREEN-MUTATE-KILL MUTANTS-REFACTOR-CLEANUP, and its
acceptance criteria are confirmed before any code is written.

### Step 1: A tournament and a match can carry `best_of` and `sets`, and missing values read as a single game

**Acceptance criteria**: The migration `supabase/sets-migration.sql` adds
`tournaments.best_of int not null default 1` and
`matches.sets jsonb not null default '[]'`, proven on local Postgres. Readers
give 1 for a tournament row without `best_of` and `[]` for a match without
`sets`.
**RED**: Unit tests for the reader helpers (row without the field → 1 or `[]`;
row with `best_of: 3` → 3).
**GREEN**: Types on `Tournament`/`Match`, the two readers, the SQL file.
`blankMatch` sets `sets: []`.
**Done when**: tests green, SQL verified locally. Applying it to production
is a separate step that needs your go-ahead and must happen before step 7
deploys.

### Step 2: The serve follows the ITTF rule across sets

**Acceptance criteria**: AC-S1-4. With A as `serve_start`: set 1 A first, set 2
B first, set 3 A first. Within a set, the every-2-points / deuce rule counts
that set's points. With `sets: []`, `serverIsA` behaves exactly as today
(existing tests unchanged).
**RED**: `serverIsA` cases for set 2 at 0-0, at 2-0, and at deuce 10-10.
**GREEN**: The first server alternates with `sets.length`.

### Step 3: The scorer knows a set ball from a match ball, and counts only true match balls

**Acceptance criteria**: In a Bo3 at 0-0 in sets, 10-9 is a « balle de set ».
At 1-1 in sets, 10-9 is a « balle de match ». At 1-0 in sets, the leader's
10-9 is a match ball and the trailer's is a set ball. In a set party there is
never a capot kind (AC-S1-5). Single-set parties keep 'match' / 'capot' as
today. Saving a set ball leaves `mb_saved` unchanged; saving a true match ball
increments it.
**RED**: Unit tests on the point-kind function and on the mb-saved decision.
**GREEN**: Set-aware `matchPointKind` and mb rule in `pingpong.ts`.

### Step 4: Validating a set, and undoing that validation, produce the right patches

**Acceptance criteria**:
- A won, non-deciding set gives `{ sets: [...sets, [a, b]], score_a: 0, score_b: 0 }`, always the whole array.
- A won deciding set gives `{ done: true, ended_at }`, and `sets` doesn't change.
- A set that isn't won gives no patch.
- At 0-0 with `sets` non-empty, undo gives `{ sets: sets.slice(0, -1), score_a, score_b }` from the last set. Once a point has been scored in the new set there is no undo patch (AC-S1-1).
- The same validation applied twice gives the same `sets`.

**RED**: Unit tests for `validateSetPatch` and `undoSetValidationPatch`.
**GREEN**: The two pure functions.

### Step 5: Realtime keeps a set validation through echoes and refetches

**Acceptance criteria**: A pending write that includes `sets` is settled only
by an echo with the same `sets`. A refetch that happens while a validation is
pending shows the pending `sets` and 0-0, never the old set's score. A pending
write without `sets` behaves as today.
**RED**: `realtimeSync` unit tests for `echoMatchesPending` and
`mergeWithPending` with `sets`.
**GREEN**: Add `sets` to `PendingValue`, the echo check and the merge.
`markPending` in `useTournament` records it.

### Step 6: The scorer runs a Bo3/Bo5 set by set (board and /ref)

**Acceptance criteria**: browser tests on `LiveScorer` with `bestOf={3}`:
- At 11-5 in set 1, « Valider le set » sends the set patch.
- The pill reads « Balle de set » / « Balle de match » (step 3).
- The meta line reads « Bo3 en 11 · Set 2 · 11-5 », following the swap (AC-S1-3).
- « Annuler » at 0-0 of set 2 sends the undo patch.
- The serve swap at 0-0 of set 2 works.
- The deciding set's validation sends `done` and calls `onFinish`.

With `bestOf` 1 (the default), every existing `LiveScorer` test passes
unchanged. `Board` and `LiveView` pass `best_of`.
**RED**: Those browser tests.
**GREEN**: Wire steps 2–4 into `LiveScorer`, and render the strip and the button label.

### Step 7: The result screen shows the scoreboard, with no capot or Slack for set parties

**Acceptance criteria**:
- After a 2-1, GameResult shows the tennis scoreboard (`11 8 11 / 5 11 9`) and the winner.
- No CapotScreen shows for a set party, even with an 11-0 set (AC-S1-5).
- No Slack invite or result goes out for `best_of > 1`. A single-set party still posts (AC-S1-2).
- Single-set GameResult is unchanged.

**RED**: A unit test for the Slack predicate (`best_of` 1 → post, 3 → no post) and for the scoreboard rows from `sets` + the final score. A browser test for GameResult if it's props-driven.
**GREEN**: The predicate used in `useTournament` and at creation, GameResult rows, and the capot guard.

### Step 8: « Nouvelle partie » offers 1 · 3 · 5 sets; 3 or 5 forces « non classée »; a rematch keeps the set count

**Acceptance criteria**:
- The chips default to 1. Picking 3 or 5 sets « Non classée » with the note « Les parties en sets ne comptent pas encore pour le classement. ». Going back to 1 restores the manual choice, like doubles today.
- `createTournament` writes `best_of`, and a rematch copies it.
- The recap and poster say « Bo3 en 11 ». The exact wording gets confirmed with you at this step.

**RED**: `enjeuEffectif` / `noteEnjeu` unit tests with sets, and a recap text test.
**GREEN**: Chips, the forced enjeu, and passing `best_of` through creation and the rematch.
**Release**: requires the step 1 migration applied to production first.
