Schema evolution · option A

Behind Slack, one pool per workspace

Today five tables sit in one open pool that anyone holding the anon key can read and write. Signing in with Slack turns the workspace ID into a tenant boundary the database itself enforces — so a bug in db.ts can't leak another company's data.

The mechanism

Where the boundary moves

The anon key ships inside the Vite bundle, and every policy today reads using (true). A login screen in React changes nothing about that — the REST API stays open to anyone with curl. The boundary has to live in Postgres.

Inventory

What each table gains

Two new tables carry tenancy; the five existing ones each take a single column. The avatars storage bucket is listed because it has its own policies and is easy to forget.

The part that keeps the diff small

Postgres stamps the tenant, not your code

lib/ holds 67 files, but nearly all of it — classement, chaos, doubles, finalStandings — is pure logic that never touches the database. The real surface is db.ts, and a column default keeps even that almost untouched: inserts get stamped by Postgres, reads get filtered by RLS.

new·the single tenancy predicate
create or replace function public.current_org_id() returns uuid
language sql stable as $$
  select nullif(auth.jwt() -> 'app_metadata' ->> 'org_id', '')::uuid
$$;

-- this default is what spares ~40 query functions from ever naming org_id
alter table public.players add column org_id uuid
  references public.orgs(id) on delete cascade
  default public.current_org_id();

create index players_org     on public.players(org_id);
create index tournaments_org on public.tournaments(org_id, created_at desc);
create index matches_org     on public.matches(org_id);

The actual risk

Two constraints are silently global

These are the migration's real hazard. Both look innocuous, both stay invisible while one company uses the app, and both fail on the second company's very first action.

Breaking · players.name

Unique across the entire database. Two companies each employing a Thomas is not an edge case — it's Tuesday. The second Thomas simply cannot be created.

Breaking · tournaments_one_active

unique (is_active) where is_active permits exactly one active tournament worldwide. Recovr starting a game would deactivate another company's live match, and their /live TV would silently switch to a tournament they've never heard of.

breaking·scope both to the org
-- players: drop the global unique, re-add it per-org
alter table public.players drop constraint players_name_key;
create unique index players_org_name
  on public.players (org_id, name);

-- tournaments: schema.sql:52 — one active row GLOBALLY becomes one per org
drop index if exists public.tournaments_one_active;
create unique index tournaments_one_active
  on public.tournaments (org_id) where is_active;

The flow you asked about

How a workspace gets detected

Signing in with Slack yields an OIDC token carrying https://slack.com/team_id. One indexed read against orgs decides whether you're joining a space that already exists or being offered the chance to create it.

Identity

Claimed players and guests

A player row with auth_user_id set has been claimed — name and avatar come from Slack. Null means a hand-created guest: the intern, the client, whoever wandered past the table. Claiming later is a single update, so an unclaimed player's Elo history survives the day they finally sign in.

new columns·players
alter table public.players
  add column auth_user_id  uuid references auth.users(id) on delete set null,
  add column slack_user_id text;   -- schema.sql has it; prod doesn't (db.ts:26)

create unique index players_org_auth
  on public.players (org_id, auth_user_id)  where auth_user_id  is not null;
create unique index players_org_slack
  on public.players (org_id, slack_user_id) where slack_user_id is not null;

Incidental win

This retires the workaround at db.ts:26 and db.ts:44, where slack_user_id is stripped from every write because the production column never existed.

A correction to what I told you earlier

Why the share link has to be a token, not a header

I suggested carrying the /live and /ref share token in a request header. That works for ordinary queries and fails for the one thing that matters most — the live scoreboard. current_setting('request.headers') is a PostgREST mechanism, and Realtime never goes through PostgREST; it authorizes on the WebSocket's own JWT.

new·what a share session may write
create or replace function public.current_scope() returns text
language sql stable as $$
  select coalesce(auth.jwt() -> 'app_metadata' ->> 'scope', 'member')
$$;

-- /ref may score, but only on the org's currently-active tournament
create policy "share link scores" on public.matches for update
  using (
    org_id = public.current_org_id()
    and (public.current_scope() <> 'share' or tournament_id in (
      select id from public.tournaments
       where org_id = public.current_org_id() and is_active
    ))
  );

Sequence matters

Migration order

These steps are genuinely ordered. A not null before the backfill fails outright, and dropping the old policies before the new ones exist leaves a window where the app is wide open.

  1. Create orgs and memberships

    Insert the Recovr row with its real Slack team id. Nothing references them yet, so this step is inert.

  2. Add org_id as nullable, with the default

    Existing rows get null, new rows would get the claim. Still inert — no policy reads it yet.

  3. Backfill every table to the Recovr org

    Five update … set org_id statements. The one step with real data at stake; take a snapshot first.

  4. Set not null, add the indexes

    Only safe once the backfill has verifiably touched every row. Check for nulls before running it, don't assume.

  5. Swap the two global constraints

    players_name_key and tournaments_one_active. There's a brief window where uniqueness isn't enforced, so do it inside one transaction.

  6. Enable Slack OIDC and the token hook

    Before the RLS change, so you can confirm a real session actually carries org_id — the one assumption I want proven rather than trusted.

  7. Replace the policies, last

    Drop using (true), install the org predicate. This is the moment the app becomes private; everything before it is reversible.

Before this becomes a spec

Two things still open

Unverified · does team_id survive?

Slack's OIDC userinfo returns https://slack.com/team_id, but whether Supabase persists that namespaced claim into identity_data is something I want to confirm rather than assume. Fallback: read provider_token once after sign-in and ask Slack directly.

Undecided · column scoping

Postgres grants are per-role, not per-claim. Restricting a share session to score columns only means either a dedicated share_scorer role with column-level grants, or a trigger. I lean role — it uses Postgres's own machinery instead of a hand-rolled check.
